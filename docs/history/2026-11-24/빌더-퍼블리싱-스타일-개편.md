- 작성일: 2026-11-24 (한국시간, Asia/Seoul)
- 상태: 검토용 설계 초안. 사용자 검토·수정 후 별도 구현 요청에 따라 적용한다.
- 분석 대상: `public/layout/builder`의 PNG 49장과 현재 빌더 소스

## 1. 요구사항과 적용 범위

### 1.1 요구사항

1. 제공된 퍼블리싱 이미지를 기준으로 `app/(siderbar-header)/admin/builder`의 빌더 스타일 변경 방향과 영향 범위를 정리한다.
2. 좌측 상단 `scenario-tab-menu`는 현재 UI와 동작을 유지한다. 이미지에 있는 단순 Unit 표시로 교체하지 않는다.
3. 기존 노드 편집, 연결, 그룹, 저장, 버전 생성, 시뮬레이터와 권한 검사를 보존하는 방향으로 설계한다.
4. 이미지에 포함된 동작 명세 중 현재 구현과 다른 부분은 스타일 수정과 구별하고, 결정이 필요한 사항으로 남긴다.
5. 실제 구현은 이 문서 검토 후 별도 단계에서 진행한다.

### 2.1 이미지 사이의 차이

- 최초 진입 및 설명용 이미지에서는 주황색 활성색·Publish와 갈색 연결선이 보인다. 라이트·다크 이미지에서는 녹색 활성색·Publish와 청회색 그룹 경계가 보인다. 단일 최종 색상 체계로 확정되어 있지 않으므로, 구현 전 대표 이미지와 강조색을 확정한다.
- 이미지의 대부분은 하나의 완성 시나리오 예시다. 예시 노드명, 내용, 날짜, 메시지 ID, 임의 JSON을 실제 데이터나 고정 UI 문구로 넣지 않는다.
- 이미지 픽셀은 화면 배율의 영향을 받는다. 100% 브라우저·캔버스 배율에서 현재 크기를 기준으로 조정하고, 원본 디자인 수치가 없으면 CSS 수치는 구현 시 비교 가능한 임시값으로 정한다.

## 3. 현재 소스 구조와 동작

이 절은 소스 정적 분석 결과다. 로그인한 브라우저에서의 실제 렌더링이나 DB 통신을 검증한 결과는 아니다.

### 3.1 상세 편집 페이지와 스타일 경로

`react-flow/scenario-flow/page.tsx`의 `ScenarioFlow`가 시나리오 목록과 선택 시나리오를 받아 `ReactFlowProvider > Flow`를 렌더링한다. `Flow`에는 툴바, 검색, 노드 추가·이동·그룹 정렬, 컨텍스트 메뉴, Flow/Orkes 전환, 저장과 모달 구성이 함께 들어 있다.

- 스타일은 `const styles = { ...sharedStyles, ...pageStyles }`로 `components/Detail.module.css`와 `ScenarioFlow.module.css`를 합친다. 같은 키는 페이지 CSS가 우선하지만, 공유 CSS의 후손 선택자까지 자동으로 차단되는 것은 아니다.
- 상단 헤더·3개 도구 그룹·분류형 라이브러리·점 배경·미니맵은 2026-10-19 작업에서 이미 일부 반영되었다. 전면 교체보다 남은 차이를 보완하는 작업이다.
- 현재 헤더 최소 높이는 42px, 도구 그룹 높이는 30px이다. 1000px 이하에서는 도구 영역을 다음 줄로 옮기며 가로 스크롤을 허용한다.
- `NodesTreeUI`는 `variant="scenario"`일 때 펼침 218px·접힘 40px이다. `NodesTree`도 같은 variant에서 분류형 팔레트를 사용한다. 실제 `treeNodes`를 사용하며 이미지에 없는 노드와 사용자 노드 설정을 More 등에 계속 제공한다.
- React Flow 배경은 `#fafafa`, 점은 간격 20·크기 1·색상 `#c7c7cc`다. 미니맵은 기본 표시하며 토글은 그래프나 undo 기록을 바꾸지 않는다.
- 우측 패널의 공유 `.controllerPanel.visible` 폭은 380px이다. `NodeController`는 명시적으로 Edit를 실행했을 때 열린다. 단순 선택으로는 열리지 않는다.

### 3.2 반드시 유지할 scenario-tab-menu

구현 위치는 `scenario-flow/page.tsx`의 `id="scenario-tab-menu"`인 MUI `Menu`와 주변 트리거다.

- 현재 트리거와 메뉴의 배치·아이콘·문구·폭·높이·선택색·닫기 버튼을 유지한다.
- 메뉴에는 열린 시나리오별 이름·버전과 타입 아이콘이 표시되며, 여러 탭일 때 닫기 버튼과 하단 Back list가 제공된다.
- `handleTabSwitch`는 현재 nodes/edges·시작 노드·선택 노드·시나리오 메타데이터를 캐시하고 대상 탭을 복원한다. 현재 탭 선택 시에는 덮어쓰지 않는다.
- `ScenarioFlow.module.css`의 `unitBadge`, `tabMenuPaper`, `tabMenuItem`, `tabKindIcon`, `tabMenuTitle`, `tabMenuVersion`, `tabCloseButton`, `tabBackButton` 및 관련 선택·hover 규칙을 보호한다. 타입·버전 해석용 `scenarioTabs.ts`도 스타일 변경 대상에서 제외한다.
- MUI 메뉴는 portal로 렌더링된다. 상단 테마나 `.editor button` 같은 넓은 선택자 변경이 트리거·메뉴에 영향을 주지 않도록 시각 회귀를 확인한다.
- 현행 타입에는 별도 불일치가 있다. `ScenarioType`과 `getScenarioType`은 `agent | multi | sub`인데 `ScenarioTabKind`는 `unit | multi | sub`다. `getScenarioTabKind`가 값을 그대로 반환하므로 `agent` 데이터의 타입·아이콘 경로는 별도 결함 후보다. 이번 설계에서는 메뉴를 수정하지 않으며, 기존 HISTORY에 기록된 `scenarioTabs.ts:7` 타입 오류와 구분해 후속 작업으로 관리한다. 현재 실행 환경에서 오류를 재현한 것은 아니다.

| 특수 노드 | `ScenarioNode.tsx`, `DelayNode.jsx`, `YnBranchNode.tsx`에 개별 UI 존재 | NodeWrapper만 고쳐서는 전체 노드 스타일이 일치하지 않음. Delay/Y-N은 제목·Edit를 표시하지 않는 현행 동작 보존 |

현재 `onDrop`에는 일반 노드 위로 라이브러리 항목을 드롭하면 두 노드를 자동 그룹으로 묶는 경로와 기존 그룹에 추가하는 경로가 이미 있다. `handleNodeDragStop`은 그룹 간 이동·그룹 해제·내부 순서 변경을 처리한다. 다만 이미지의 좌우 + 버튼과 작은 Node Picker는 현재 공통 노드에 없으며, 삽입에는 기존 `ActivityPickerModal`과 `openActivityPicker`/삽입 대상 구조를 재사용할 수 있는지 검토해야 한다.

또한 현재 그룹 편입 경로에는 이미지 8·9의 “Branch 경로가 합류하는가”에 따른 허용·차단 판정이 없다. 화면의 Branch를 마지막 자식으로 정렬하는 처리와 실행용 분기 보존은 별개로 존재하므로, 이 정책을 CSS 변경으로 처리할 수 없다.

### 3.4 우측 속성 패널

- `NodeController.tsx`가 노드 타입별 `components/controllers/*Controller`를 선택하고, `localNode`를 편집한 뒤 Save Changes에서 기존 상태에 반영한다.
- 패널 내부에는 `Type: ...` 헤더와 폼, 하단 저장 버튼이 있다. 이미지의 타입 아이콘·이름·닫기 헤더, BASIC/BEHAVIOUR/SYSTEM 구분과는 구조 차이가 있다.
- `NodeController.module.css`는 입력폼·목록·폼 요소 등 여러 타입의 편집 UI에 공용으로 사용된다. 개별 Controller에는 MUI와 인라인 스타일도 있으므로 공용 CSS만 변경하면 불일치가 남는다.
- 현재 `isDirty`는 해당 속성 패널의 로컬 데이터와 선택 노드 데이터를 비교한다. 시나리오 전체의 미저장 여부를 뜻하지 않는다.
- 이미지의 Language, translations, modal response 등 현재 모든 노드에 없는 필드는 새로 만들지 않는다. 기존 필드를 의미에 맞게 묶는 것이 기본 방향이다.

### 3.5 상태·저장·권한·테마

- 실제 편집 상태와 저장 경로는 `store/index.ts`의 `useBuilderStore`다. `store/slice/*`에 비슷한 함수가 있어도 현재 페이지에서 사용하는 store를 우선 추적한다.
- 저장은 `sanitizeNodesForSave`/`sanitizeEdgesForSave`를 거쳐 `nodes`, `edges`, `startNodeId`를 기존 서비스로 전달한다. 외형 변경으로 ID, `parentNode`, `groupOrder`, 핸들 ID나 데이터 의미를 바꾸지 않는다.
- Save는 `version_yn:false`, Publish는 `version_yn:true`로 같은 `saveScenario`를 호출한다. 현재 Publish는 버전 생성이며 실제 배포용 `scenarioVersionDeploy`와 다르다. 이미지의 Published/“Published to the chatbot”를 그대로 표시하면 실제 동작과 맞지 않는다.
- `saveScenario`는 성공·실패에 기본 alert를 사용하며 실패를 내부에서 처리한다. 단순히 `await`가 끝났다는 이유로 저장 성공 상태를 표시하면 안 된다. 신규 저장 상태 표시를 채택하면 기존 `onSuccess`/`onError` 등 실제 성공 경로를 사용해야 한다.
- 이 페이지에는 시나리오 전체 dirty 기준점과 미저장 이탈 가드가 없다. `goList`는 `router.back()`을 실행한다. Last saved·Published 문구를 고정값으로 추가하지 않는다.
- 빌더의 `DB_TYPE`/서비스 선택은 `firebase | fastapi`, 기본값은 `firebase`다. 포털 일반 기능의 `NEXT_PUBLIC_BACKEND=postgres`와 동일한 분기로 간주하면 안 된다. 현재 Firebase는 직접 SDK, FastAPI는 외부 `/chat/builder/scenarios...` 서비스를 사용한다. 스타일 적용에는 백엔드 변경·DB 작업이 필요하지 않다.
- `proxy.ts`가 `/admin/**`에 SSO·관리자 이메일 검사를 적용한다. `aiEnabled`는 `/chatbot`, `/api/chatbot` 경로 검사이며, 빌더 화면에 새 권한 규칙을 추가하는 요구는 아니다. 노드 수정의 `unuseNodes` 검사도 유지한다.
- 전역 `useStore`에 theme 상태·설정 저장이 있지만, 빌더의 CSS·인라인 값은 대부분 밝은 색을 고정한다. 기존 theme를 읽어 적용하는 설계가 필요하다. `setTheme`는 사용자 설정을 Firestore에도 기록하므로, 단순 빌더 테마 반영 과정에서 새 저장 호출을 추가하지 않는다.

## 4. 수정 방향

### 4.1 페이지 범위 스타일과 테마

1. 기본 적용 범위를 상세 편집 화면으로 제한한다. `ScenarioFlow.module.css`의 페이지 클래스와 선택적 presentation variant/context를 사용한다.
2. 공유 노드와 Controller에는 이 화면에서만 활성화되는 variant를 전달하고, 다른 화면은 기존 기본값을 유지한다. DOM 후손 선택자만으로 portal 내부 메뉴까지 제어할 수 없으므로 Popover paper에 명시적으로 스타일 범위를 전달한다.
3. 배경, 패널 표면, 경계, 본문·보조 글자, hover, 선택, 강조색, 타입별 색을 CSS 변수로 묶는다. 헤더·팔레트·노드·속성 패널·미니맵이 같은 값을 참조하도록 한다.
4. 다크 모드는 기존 theme 상태를 읽고 페이지 범위 변수만 전환하는 안을 권장한다. 라이브러리의 white 혼합 배경·입력폼·비활성·Popover·툴팁까지 확인한다. 시나리오 메뉴는 보호 예외로 유지한다.
5. `nodeColors`와 사용자별 노드 설정은 계속 반영한다. 이미지의 타입 색상은 기본값 후보이며 사용자 설정을 일괄 덮어쓰지 않는다.

### 4.2 상단·라이브러리·캔버스

- 기존 3개 도구 그룹을 유지하면서 버튼 높이·간격·테두리·활성/비활성 색을 정리한다. 각 아이콘의 실제 handler와 tooltip을 일치시킨다.
- 이미지에 없는 Flow/Orkes, 검색, 노드 설정, 추가 노드 타입도 기존 접근 경로를 유지한다. 현재 Sparkles는 시뮬레이터 열기이므로 이미지 설명만 보고 AI Generate 기능으로 이름을 바꾸지 않는다.
- 좌측 팔레트는 기존 카테고리와 실제 설정 데이터를 유지한다. 접힘 상태에서도 재열기 버튼을 키보드로 사용할 수 있게 한다.
- 캔버스·미니맵의 색상·경계·여백을 맞춘다. 헤더 줄바꿈과 좌우 패널 개폐 후 남은 영역을 정상적으로 채우도록 `min-width:0`, `min-height:0` 및 내부 스크롤을 확인한다.
- 이미지의 Expand All/Collapse All은 신규 명령 후보로 분리한다. 현재 그룹 접기와 일반 노드 본문 접기는 다른 상태이므로, 대상이 그룹만인지 내부 노드 본문까지인지 먼저 확정한다. Fit은 화면만 조정하고 그래프를 재배치하지 않는다.

### 4.3 공통 노드와 그룹

- 타입별 얇은 경계와 은은한 표면, 작은 아이콘·보조 타입명, 제목 말줄임, 낮은 높이의 접힌 헤더를 구성한다. 기본·hover·선택·시작·앵커·실행 중·실행 완료 상태가 함께 구별되도록 한다.
- 선택은 큰 파란 그림자보다 얇은 ring을 기본안으로 하되 테마별 강조색은 검토 후 정한다. 오류 상태는 실제 검증 결과가 있을 때만 배지·툴팁을 표시한다.
- 제목은 전체 값을 저장하고 표시 영역에서 말줄임한다. 이미지의 “최대 11글자 표시”를 데이터 길이 제한으로 해석하지 않는다.
- Edit는 펼친 본문 안에서 우측 정렬한다. 선택·드래그·본문 접기와 이벤트가 충돌하지 않게 `nodrag/nopan` 및 기존 전파 제어를 보존한다.
- 그룹은 노드 수 배지 + 이름 + ellipsis가 중심인 헤더와 안쪽 여백을 갖게 한다. 수는 실제 직접 자식 수로 계산하며 저장 필드를 추가하지 않는다. 설명문·그룹 Edit·시작/앵커 등의 기존 기능을 옮기거나 감출지는 결정표에 따른다.
- 그룹 하단의 기존 Add Node를 작은 원형 +로 바꾸는 안을 제안한다. 부모 안쪽 또는 경계 안에 배치하고 hover 외 키보드 focus에서도 표시하여 버튼까지 이동할 때 사라지지 않게 한다.
- 크기를 바꿀 경우 공통 표시 치수와 페이지/store의 그룹 배치 상수를 함께 검토한다. 우선 실제 노드 측정 높이를 사용하고, 기존 절대 위치와 상대 위치를 보존하며 부모 경계를 계산한다. CSS `transform:scale`로 크기만 줄이지 않는다.
- 크기·접힘·제목 줄바꿈 변화 뒤 `useUpdateNodeInternals`를 호출하는 현행 경로를 보존한다. 연결 좌표·저장된 꺾임점 처리까지 확인한다.
- 그룹 순서선·핸들의 시각 변경은 별도 결정 후 적용한다. 보이게 하더라도 실행용 edges를 새로 생성하거나 핸들 ID를 바꾸지 않는다. API `onSuccess`/`onError`, Branch/Y-N 경로는 유지한다.

### 4.4 더보기·연결선·우측 편집기

- 노드 더보기는 텍스트와 아이콘을 함께 보여 주는 목록형 스타일로 정리하는 안을 제안한다. Edit는 기존 `handleEditNode` 경로로 연결한다. 현재 시작·앵커·API 테스트·Ungroup 기능을 잃지 않도록 메뉴 구성 결정을 먼저 받는다.
- 노드 더보기와 캔버스 우클릭 메뉴는 진입 위치와 제공 명령이 다르다. 하나를 없애거나 모든 명령을 같은 것으로 바꾸지 않는다. 화면 끝 overflow, portal, Escape, focus 복귀를 검증한다.
- 연결선은 기존 경로·선분 드래그를 유지하며 색·두께·chip 모양을 바꾼다. Branch의 A/B/C/Default 표시는 표시용 순번과 실제 `sourceHandle`을 분리한다. 현재 번호 label을 바꾸더라도 저장 핸들 ID를 알파벳으로 치환하지 않는다.
- chip 툴팁을 채택하면 실제 조건이나 reply 내용을 조회해 표시하고 DOM 접근 가능한 설명을 제공한다. tooltip이 연결·선분 드래그를 방해하지 않게 한다.
- 우측 패널은 아이콘·타입명·닫기 버튼이 있는 고정 헤더, 스크롤되는 폼, 고정 하단 Save Changes 영역으로 구성한다. 닫기는 편집 패널 표시 상태를 해제하는 callback으로 연결한다.
- 속성 구분선·라벨·입력 높이·버튼·read-only 표면을 공통화한다. BASIC/BEHAVIOUR/SYSTEM 구획은 기존 필드만 재배치하고, 타입별 Controller의 입력·검증·임시값·저장 의미를 보존한다.
- 좁은 화면의 우측 패널은 캔버스 폭을 모두 소모하지 않도록 제한 폭 또는 임시 overlay를 검토한다. 최종 반응형 방식은 결정 대상이다.

## 7. 구현 순서 제안

1. D1~D3으로 기준 이미지·색상·범위를 정하고 현행 화면과 메뉴의 비교 이미지를 남긴다.
2. 페이지 범위 변수·variant를 도입하고 헤더·팔레트·캔버스·미니맵의 외형을 맞춘다.
3. 공통 노드·특수 노드·그룹·엣지와 우측 패널을 맞추고 크기 계산·portal 동작을 검증한다.
4. 결정표에서 채택된 기능만 별도 변경 단위로 구현한다. 저장·그래프·실행 변경이 있으면 관련 회귀 검증을 추가한다.
5. 메뉴 보존과 다른 화면 영향, 저장 payload 호환성을 확인한 뒤 문서에 실제 변경 파일·결과를 기록한다.

### 8.3 데이터·실행·개발 검증

- 스타일 적용 전후 같은 시나리오의 저장 payload를 비교한다. 순수 스타일 변경에서는 ID·연결·시작 노드·분기 조건·소속이 같아야 한다. 그룹 표시 크기 계산의 변경이 저장되면 의도된 치수 차이만 설명한다.
- 실제 저장 검증은 별도 테스트 시나리오에서 수행한다. Firebase와 FastAPI의 Save·버전 생성·실패 후 상태를 각각 확인하고, 운영 DB를 검증 대상으로 사용하지 않는다.
- 그룹 API 성공은 아래 자식으로, 명시적 Error는 해당 경로로, Error 미연결은 기존 그룹 순서로 진행하는 동작을 확인한다. 일반 분기·Y/N·그룹 끝 복귀도 유지한다.
- 소스 변경 후 저장소 기준 `pnpm lint`, `pnpm build`를 수행한다. `pnpm exec tsc --noEmit --pretty false`로 타입 결과를 분리 확인할 수 있다. 기존 `scenarioTabs.ts` 타입 불일치가 남아 있으면 새 오류와 구분해 기록한다.
- 그래프·저장·실행 로직을 실제로 바꿀 경우 해당 시나리오를 다루는 기존 회귀 테스트를 실행하거나 필요한 동작 테스트만 추가한다. 외형 검증을 위해 구현을 그대로 복제하는 테스트는 추가하지 않는다.
- 최종 완료 조건은 승인한 이미지 기준의 화면 일치, scenario-tab-menu 보존, 기존 편집·저장·실행 호환, 공유 화면 영향 통제, 변경 파일·검증 결과 기록이다.
